# Portfolio site

Static Next.js site with a WebGL fluid-simulation backdrop. Deploys as plain
files — no database, no serverless functions, no environment variables.

```bash
npm run dev           # http://localhost:3000
npm run build         # static export into ./out
npm run lint          # Biome
npm run lint:fix      # Biome, applying safe fixes
npm run placeholders  # regenerate placeholder imagery
npm run tokens        # Claude Code token usage for this project
```

## Tooling notes

**Biome, not ESLint.** `next lint` was removed in Next 16, and the replacement
`eslint-config-next` depends on `typescript-eslint`, which refuses to load
under the TypeScript 7 native compiler this project uses ("typescript-eslint
does not support TS 7.0"). Biome parses TS natively with no such coupling, and
is what the Next 16 upgrade guide recommends. Revisit if
[typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940)
lands.

Rules switched off in `biome.json` are deliberate, and each carries a reason:
`noImgElement` (static export means `next/image` adds nothing and breaks on the
SVG placeholders), plus several false positives against `FluidCursor.jsx` —
Biome reads `gl.useProgram` as a React hook.

**QA harness.** `scripts/shot.mjs` drives real Chrome via puppeteer to
screenshot any route at any viewport, reporting console errors, failed
requests, and horizontal-overflow numbers. Measure the fluid by screenshot,
never by reading pixels off the canvas — `preserveDrawingBuffer: false` means
canvas readback returns empty even when the effect is rendering correctly.

## Where to edit what

Almost all iteration happens in `src/data/`. The components read from these
files and do not hardcode content.

| File | Holds |
|---|---|
| `src/data/profile.ts` | Name, hero headline, the three claims, About prose, outbound links |
| `src/data/experience.ts` | Roles, split by `track` (defense / commercial). `bridge` marks the crossings |
| `src/data/projects.ts` | The six projects, their galleries, and `span` (drives the mosaic composition) |
| `src/data/athletics.ts` | Running and triathlon PRs |
| `src/data/travel.ts` | Places, as `[longitude, latitude]` |
| `src/data/play.ts` | The four hobby tiles |

Everything currently marked `TODO` or "Placeholder" is a guess written to make
the layout legible. None of it is your real history, times, or travel.

## Images

Placeholders live in `public/images/` and were generated by
`scripts/make-placeholders.mjs`. Drop real photos in at the same paths — the
app does not care that the placeholders are SVG. Update the paths in the data
files if you rename anything.

For the hero backdrop, put a photo at `public/images/backdrop.jpg` and set
`BACKDROP_IMAGE` in `src/components/Backdrop.tsx`. Until then a gradient mesh
stands in.

## Design decisions worth knowing before changing things

**The content wrapper in `layout.tsx` has no `z-index`, on purpose.** Any
z-index creates a stacking context, and a stacking context isolates blending —
which would break the hero headline's `mix-blend-mode`, the one effect letting
the fluid paint through the type. Plain `relative` still stacks above the
backdrop by DOM order.

**`FluidCursor` must not call `loseContext()` on unmount.** The original
reference component did, and it made the effect render nothing at all in dev. A
WebGL context belongs to the `<canvas>` element, not the React component — and
under Strict Mode, React mounts, unmounts, and remounts onto the *same* canvas
node. Force-losing the context on that first teardown permanently bricks it:
the remount's `getContext()` returns the same dead context and every draw call
silently no-ops against a transparent canvas. Deleting the framebuffers,
textures, programs and buffers is what actually reclaims GPU memory; the
`loseContext()` call was pure downside. Do not reinstate it.

**The hero headline uses `mix-blend-mode: difference`, not `multiply`.**
Multiply outputs `backdrop x source`; with the ink source already near-black the
result is near-black whatever the fluid does, so it was mathematically
incapable of tinting the type. `difference` with a white source outputs the
inverted backdrop — near-black over the pale ground, so contrast holds (measured
at 18.45:1 under maximum dye accumulation), while the letterforms take the
complement of the fluid as it passes. The `@supports` guard is load-bearing:
without blending, white type on a light ground is invisible.

**`corner-shape: squircle` is progressive.** The `.sq*` classes give true
G2-continuous corners where the browser supports `corner-shape`, and fall back
to plain `border-radius` elsewhere. If you need guaranteed squircles in every
browser, that means a JS-driven `clip-path` per element — worth it for a few
hero elements, not for every card.

**Glass has three tiers, and they mean something.** `.glass-1` is chrome (nav),
`.glass-2` is a standing panel, `.glass-3` is foreground over imagery. Do not
flatten them into one card style — the hierarchy is the point.

**The projects mosaic is hand-composed.** The `span` values resolve exactly
against a six-column grid across three rows. Reordering `projects` will change
the composition; check it still resolves.

**Fluid parameters are measured, not guessed.** See
`reference-material/HANDOFF.md` before changing any of them. `PRESSURE: 0.1` in
particular is what makes the fluid read as thick liquid rather than gas, and it
is not obvious from the name.

## Deploying

Vercel, Netlify, Cloudflare Pages, or GitHub Pages all work — the build output
is static files. On Vercel, importing the repo is enough; it detects Next.js
and the `output: "export"` config does the rest.

## Known exceptions and follow-ups

**`useSemanticElements` is disabled for `WorldMapView.tsx`.** Biome wants HTML
`<button>` semantics for the map pins, which cannot be expressed inside an
`<svg>`. The current `<circle role="button" tabIndex={0}>` pins were verified to
take keyboard focus in DOM order, show both focus indicators, and respond to
Enter and Space without scrolling the page.

The remaining weakness is browse-mode screen-reader navigation: the pins are
reachable by Tab but are not announced as interactive when arrowing through the
page. The real fix is to render pins as absolutely-positioned HTML `<button>`s
over the SVG, keeping the SVG for geography only. That would also let the hit
targets be sized in CSS pixels rather than viewBox units. Worth doing when the
travel page gets real content.

**The fluid effect has a `?fluiddebug=1` mode.** Loading any page with that
query string shows a badge naming the exact branch the component took —
`fluid:webgl2`, `fluid:webgl1`, `still:prefers-reduced-motion`,
`css:no float render targets`, or `css:webgl context lost`. It is the fastest
way to diagnose the effect on a device you cannot attach a debugger to.
